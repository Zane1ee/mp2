WORKLOAD AND DIFFICULTY
-----------------------
- Difficulty: medium-high. The main additions to MP1 are typed remote data,
  asynchronous state, three routes, filter-aware detail navigation and static
  hosting of deep links.
- Original planning estimate: three pages, several shared components, about
  800-1,300 business-code lines and 250-450 CSS lines. Estimates are guidance,
  not grading requirements or promises of completion time.
- Prioritize List (28), Gallery (12), Detail (38), required tools (12) and Design
  (10). Implement both detail entrances and navigation early.
- Principal risks: duplicate/bulk requests, late responses, invalid/missing
  fields, partial type indexes, mutable sorting, lost source context, Pages base
  paths, Node compatibility and inaccurate submission records.
- Keep the approved scope. Authentication, favorites, evolution trees, pagination
  and elaborate animation are outside this version.

STEP 4: MAP REQUIREMENTS TO THE THREE VIEWS
------------------------------------------------------------
Actions:

    count, semantic result links and loading/error/empty states. Filter names
    while typing, ignoring case and outer whitespace; sort every matching item.
  - Gallery: API-provided images, names/IDs/types, actual type checkboxes, Clear,
    result count and links to the shared detail route. Missing images use an
    accessible placeholder; decorative art is not a substitute for item media.
  - Detail: back-to-source link, name/ID, image, types, measurements, abilities,
    base stats, Previous/Next and collection position. Identity comes from the
    route ID, including on direct access and refresh.
Verify:
  - The routes are distinct views in one SPA. Both entrances show the correct
    object's fields and retain the appropriate source collection.

STEP 6: PREPARE API, ENVIRONMENT AND REFERENCES
------------------------------------------------------------
Actions:
  - API base: https://pokeapi.co/api/v2/.
    Catalog: GET pokemon?limit=60&offset=0; detail: GET pokemon/<id>/.
  - Validate IDs/names/types; map optional images and nullable measurements.
    Height / 10 is meters; weight / 10 is kilograms. Show Unavailable for missing
    optional data rather than inventing values. Use image URLs returned by API.
  - Require Node/npm, browser, network and the existing repository. No mandatory
    MCP, Python runtime, Docker, .env, database or API account is needed by the app.
  - Verify browser JSON/CORS/media behavior. Use shared cache and no more than
    four concurrent detail requests; a complete cold Gallery needs catalog plus
    60 details, excluding images and explicit retries.
  - Register all reading, starter/tool and API/media sources in SOURCES.md.
Verify:
  - The free API and images work from the deployed origin. Never assume a VITE_*
    variable hides a client credential; any future API change requires review.

------------------------------------------------------------
STEP 7: DEFINE URL, FILTER AND ASYNCHRONOUS SEMANTICS
------------------------------------------------------------
Actions:
  - List uses q/sort/order, stable text/numeric comparisons and copy-before-sort.
    Clear removes the query and retains sorting; edits replace browser history.
  - Gallery validates/deduplicates repeated type parameters; OR results are
    unique and in ID order. Enable type filters/navigation only when the full
    type index is available. Partial failure is not a valid zero-result filter.
  - from=list reconstructs List order; from=gallery reconstructs Gallery order.
    No source uses the default collection. A mismatched current ID shows an
    explicit full-collection fallback and persists browse=all; Back keeps filters.
  - Carry mode=sample across views and navigation. Keep live/sample state isolated.
  - Distinguish idle/loading/success/error. Cache requests by ID, prevent late
    responses from replacing another profile, and preserve shared request ownership.
Verify:
  - Direct URL, refresh, history and Back give deterministic order independent
    of response timing. Cover empty/singleton/multi-item and malformed parameters.

------------------------------------------------------------
STEP 8: DEFINE SEMANTIC AND RESPONSIVE UI
------------------------------------------------------------
Actions:
  - Use skip link, header/nav/main/footer, one main heading and real labels.
    Links navigate; buttons/inputs act. Use ul/li, dl, Grid and Flex for content.
  - Use classes/CSS Modules rather than style attributes or dynamic .style.
    React onClick/onChange handlers are valid and are not inline script tags.
  - Give images alt text and broken-image placeholders. Expose checked/disabled,
    progress and error states without relying on color alone.
  - Recommended sizes: 1440x900, 1024x768, 768x1024, 390x844 and 320x800.
    Wrap controls/fields, retain visible keyboard focus and respect reduced motion.
Verify:
  - Core actions work without overflow/overlap. Route changes focus the heading;
    query edits retain control focus; retry recovery does not lose focus.
